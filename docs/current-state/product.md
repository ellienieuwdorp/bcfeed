# bcfeed: product overview

What bcfeed is, who it is for, how it got here, and what it believes. Condensed from the full audit evidence base and re-validated against `main` @ e363bf4 (the IMAP-provider merge, 2026-07); citations are file:line in this repo, screenshots in `docs/current-state/screenshots/` (which predate the settings-UI redesign), and finding IDs from the verified audit.

## Goal

Bandcamp fans who follow many artists and labels get one "New release from X" email per release — unmanageable at volume in a mailbox. bcfeed turns that email pile into a local, browsable, filterable, sortable release dashboard with inline Bandcamp players: a personal "new releases feed" Bandcamp itself doesn't offer (README.md:5-7).

Technically it is a local Flask server (server.py, 822 lines) launched from a CLI entrypoint that opens `http://localhost:5050/dashboard` in the default browser (bcfeed.py:32-51), serving a no-framework single-page app (dashboard.html 306 lines, dashboard.js 2113 lines, dashboard.css 1058 lines). The "local database" is seven JSON files in `~/Library/Application Support/bcfeed` (paths.py): release cache keyed by date, embed cache keyed by URL, viewed/starred sets, scrape-status ledger, empty-dates memo, and (new at e363bf4) `provider_config.json`. Secrets no longer live on disk: the Gmail OAuth client secret, the Gmail token, and any IMAP password are held in the system keychain via `keyring` (credential_store.py).

## Target user

A music lover with a Bandcamp fan account and an email account. As of e363bf4 that account can be **either a Gmail account (via the official Gmail API/OAuth) or any IMAP-compatible mailbox** — Gmail, iCloud, Outlook, Fastmail, etc. — configured with server/username/password in the Settings panel (README.md:8-12, SETUP.md:53-61). The docs still address two personas — "power users (Homebrew already installed)" and "beginners" told what a Terminal is — but the realistic user is semi-technical: comfortable keeping a Terminal window open, and (for Gmail) able to survive the Google Cloud Console. The primary user is plainly the author; single-user, personal-use assumptions are everywhere ("Since this OAuth client is used **only by you**", GMAIL_SETUP.md; one global viewed/starred set; one populate at a time, server.py:59). Volume assumptions: heavy follower, hundreds of notification emails a month, default cap of 2000 results per search (server.py:60).

## Core loop

0. (First run) Pick a provider in Settings — Gmail API (OAuth) or IMAP — and supply credentials. IMAP additionally has a "Connect & load folders" step that discovers and recommends which mailbox folder to scan (server.py:717-752).
1. Select a date range on the calendar (which doubles as a coverage/unread map — the app's best IA idea).
2. Click "Populate release list": provider search + email parse, with SSE-streamed progress into a status log (README.md:17-26).
3. Browse the table (Label/Page, Artist, Title, Date; dashboard.html:88-99). Expand a row to lazily load the Bandcamp embed player and scraped description/credits — or click "Preload release data" to prefetch in bulk, or star releases (starring triggers background preload) and browse via the Starred filter.
4. Mark seen / filter by label, unseen, starred. Keyboard triage shortcuts exist (arrows, s, u, Escape) but are documented nowhere (UX-14).

See `10-populated-dark.png` (populated table + calendar), `12-row-expanded-dark.png` (embed detail), `13-starred-filter.png`. Caching is aggressive and permanent: a populated range never needs re-populating, and — documented caveat — never *can* be re-populated except via destructive cache reset (README.md:30; UX-12). Bandcamp scraping is slow by design ("a few seconds per release", README.md:37-47), so the whole workflow section of the README is really a coping guide: preload, or star-then-browse.

## Development history: three eras

285 commits, 2022-05 → 2026-01. Author: TJ Hertz (keinobjekt); the two external PRs ever merged are Hank Jackson's (2024). This working copy's remote points at ellienieuwdorp/bcfeed with no tags.

**Era 1 — CLI script (2022-05 → 2024-09).** `BandcampSummary.py`: batch-download Gmail messages, emit static HTML pages of player widgets. Key reversal: 2022's "scrape the Bandcamp page for details" (7964240) was undone in 2025 (af03402) — the mature design scrapes cheap metadata from the email and defers expensive Bandcamp scraping to lazy/preload time. `credentials.json` was committed and removed twice in this era.

**Era 2 — App-ification burst (2025-12, 155 commits in one month).** After a 14-month gap the script became a product: the dashboard SPA, embed proxy, tkinter server GUI, settings modal (added mid-history, b69662c), session persistence, seen/starred state, rename to **bcfeed** (7c23b77), data moved to Application Support, first PyInstaller packaging attempts (abandoned), then a late-December UX blitz: calendar range panel, SSE-streamed populate, OAuth error handling, credentials management moved into the browser.

**Era 3 — Consolidation and distribution (2026-01, 77 commits).** Starred filter; static dashboard + runtime config instead of HTML regeneration; systematic per-file "code review done" commits; the 2323-line dashboard.html split into HTML/CSS/JS; v1.0 label in the header (dashboard.html:73); **tkinter GUI deleted entirely** (4c29b36) to retry packaging; Homebrew formula added then immediately moved to a separate tap (c0e73ab/0030854); docs restructured into README/SETUP/GMAIL_SETUP served in-app. Final commit (598a9dd, 2026-01-26) blocks selecting today in the calendar — reflecting the pervasive "today is never final" cache logic (session_store.py:74-78, 179, 198).

What churned most: the frontend monolith (100+ commits, whole-UI reorganizations); packaging (PyInstaller built and deleted, GUI built and deleted, formula in-repo then out); docs (renamed/split/rewritten repeatedly); naming (cached→populated, seen→viewed, Populate→Get releases→Populate). TODO.rtf has exactly one open item: "package in executable with installer".

**Post-audit — the IMAP-provider merge (e363bf4).** After the audit baseline (598a9dd), this working copy fast-forwarded to e363bf4, a large PR (+2724/−464 across 21 files) that reshaped the source: an email-provider abstraction (`email_provider`, `gmail_provider`, `imap_provider`, `provider_factory`) so populate can source emails from Gmail **or** generic IMAP; `gmail.py` split into `gmail_client` + `gmail_provider`; the email-parsing heuristics extracted into `bandcamp_email_parser` and subject-gated; keychain-backed credential storage (`credential_store`, `keyring`) replacing `token.pickle`; a redesigned Settings panel; the hand-rolled markdown renderer replaced by markdown-it-py; and an empty-email-body crash fix. IMAP is therefore no longer aspirational — it ships. Several audit findings shift as a result (see Tensions); the "package in executable" TODO item remains open.

## Distribution model

**Current channel: Homebrew tap.** `brew tap keinobjekt/bcfeed && brew install bcfeed` (SETUP.md:11-12). A `Language::Python::Virtualenv` formula with every dependency pinned as a resource stanza, sourcing the keinobjekt repo at tag v1.0-beta2. Consequences: the tap and this repo can drift; the UI version string is hardcoded, not derived; the formula uses python@3.11 while `.python-version` says 3.10.19 and SETUP.md says "3.10 or newer"; requirements.txt is unpinned and still uses the `bs4` shim, and at e363bf4 it also added `keyring`, `markdown-it-py`, and `linkify-it-py` (and dropped the earlier duplicate `requests`) — new runtime dependencies the pinned formula in the tap does not yet reflect, widening the drift (ARCH-9).

**Aspirational channel: standalone .app.** The TODO's sole open item. Two packaging campaigns failed; remnants survive as a `sys._MEIPASS` check in gmail_client.py:52-54 that would bundle an OAuth client secret into a distributed binary — contradicting the user-owned-credentials model — while the assets that *would* need bundle awareness have none (paths.py:30-36). The keychain dependency (`keyring`, credential_store.py) adds a runtime requirement any packaged build must satisfy: a working system keychain backend (present by default on macOS).

**Structural constraint:** the product is a resident local server + browser tab, so every channel must solve "keep a process alive". Hence the thrice-repeated "keep the Terminal open" instruction (SETUP.md:17, 33, 49), the 5-second health poll with a restart modal (client-side in dashboard.js against `/health`, server.py:169-181), and the standing desire for a real .app. Data survives install/uninstall because it lives in Application Support.

## Fundamental principles

1. **Local-first / your data stays yours.** Everything on localhost, all caches local JSON, explicitly no analytics/telemetry/remote logging (privacy.md; README.md:68-72).
2. **Privacy via user-owned credentials.** No hosted service, no verified OAuth app: each user either creates their own Google Cloud OAuth client (GMAIL_SETUP.md) or connects their own IMAP mailbox with their own server credentials/app password. Privacy is achieved by pushing infrastructure onto the user. New at e363bf4: the resulting secrets (Gmail client config, Gmail token, IMAP password) are stored in the OS keychain rather than as plaintext/pickle on disk (credential_store.py; privacy.md:11, README.md:41).
3. **Single user, personal tool.** No accounts, one global viewed/starred set, one populate at a time (server.py:59), "for your personal use only" (GMAIL_SETUP.md).
4. **Never re-fetch; cache aggressively and permanently.** Per-day scrape ledger, empty-range memoization, append-only release cache (session_store.py throughout; README.md:30). Corollary: today is never final — systematically excluded from being marked scraped.
5. **Be polite to upstream.** Batched Gmail fetches with 429 handling and max-results guardrails (gmail_client.py:267-313), read-only IMAP folder selection (imap_client.py:110), and lazy user-initiated Bandcamp scraping with 10s timeouts and a `bcfeed/1.0` UA (server.py:487-491).
6. **Practicality over polish or stack purity.** Vanilla JS, no framework, no build step, honest low-promise docs ("It probably won't work on Windows, but feel free to try", README.md). No tests anywhere. (The hand-rolled markdown renderer was retired at e363bf4 in favor of markdown-it-py — a rare move toward a dependency.)
7. **Progressive de-scoping toward simplicity.** tkinter GUI deleted, HTML regeneration deleted, two calendars merged into one, duplicate endpoints collapsed. The codebase repeatedly got smaller on purpose.

## Tensions

Where the implementation contradicts the principles the project holds. These are the credibility gaps to close before (or alongside) any cosmetic work.

**1. Full-mailbox OAuth scope vs the read-only promise (SEC-3, high/confirmed — still present at e363bf4).** GMAIL_SETUP.md and SETUP.md title the step "Add Gmail read-only API scope" and have the user paste `gmail.readonly`; privacy.md implies read-only behavior. But gmail_client.py:217 still requests `https://mail.google.com/` — full read/send/delete — with an in-code comment saying exactly that. The consent screen shown to the user contradicts the setup doc they just followed. The app only ever calls `messages().list/get`, so the broad scope buys nothing. This remains the sharpest privacy finding and a one-string fix. **What changed:** the storage half of this tension is resolved — the over-provisioned token is no longer an unencrypted pickle with default file perms; it now lives as JSON in the system keychain (credential_store.py; SEC-5's at-rest concern addressed). The excessive *scope* it grants is unchanged. (A residual `pickle.load` path survives only to migrate a pre-existing legacy `token.pickle` into the keychain once, gmail_client.py:128-144.)

**2. `0.0.0.0` bind + `Access-Control-Allow-Origin: *` vs local-first (SEC-1, SEC-2, SEC-4 — still present at e363bf4).** "Everything runs on localhost" is the core promise, but the server still binds `0.0.0.0` (server.py:186, and again in the `__main__` `app.run` at server.py:822), exposing an unauthenticated API — credential upload (`/load-credentials`), credential wipe, cache wipe, provider reconfiguration (`/provider-config`, `/imap/discover` — which will open an IMAP connection using posted or stored credentials), and the `/embed-meta` open-URL fetcher (server.py:479-512, an SSRF proxy with no allowlist) — to the entire LAN. Every response carries `Access-Control-Allow-Origin: *` with no Host/Origin validation (server.py:87-91), creating a CSRF/DNS-rebinding surface from any website. Both fixes are cheap (bind loopback; drop ACAO:* and allowlist /embed-meta); until then the privacy posture is aspirational, not actual.

**3. The onboarding wall vs the beginner persona (UX-1, UX-2, UX-5, high/confirmed — partially eased at e363bf4).** SETUP.md explicitly courts beginners who need "Terminal" explained. For the Gmail path the wall is unchanged: create a Google Cloud project, enable an API, configure a consent screen, paste a scope URL, publish "In Production", download a client secret, and click through Google's "unsafe app" interstitial (GMAIL_SETUP.md; realistically 20-30 minutes with known failure modes). The credential upload still silently blocks on an OAuth browser flow the UI never announces (server.py:609 → gmail_client.py:216-236; SEC-6/UX-2). **What changed:** the Settings panel was redesigned (Appearance / Email Configuration / Data & Storage sections) and now offers **IMAP as an alternative that sidesteps the Google Cloud Console entirely** — host/username/password plus a "Connect & load folders" step that auto-discovers and recommends the right folder (server.py:717-752, IMAP_SETUP.md). This meaningfully lowers the first-run wall for users on iCloud/Fastmail/etc., though IMAP brings its own friction (many providers require enabling IMAP and/or an app-specific password) and the screenshots in this folder predate the redesign. The first-run empty state and the general "usable without reading docs" gap remain.

Lesser but real: "never re-fetch" still turns transient failures into permanent silent data loss because days are marked scraped before releases are persisted (ARCH-2/PY-1, unchanged at pipeline.py:162/183); the docs call it "a macOS desktop app" when it is a local web app with a CLI launcher; the header says v1.0 while no release tag exists in this repo (ARCH-9); and there is no LICENSE file despite the formula declaring MIT and past external contributors. Newly dead as a side effect of the provider abstraction: the max-results guardrail — `provider.search` truncates to `max_results`, so `MaxResultsExceeded` (and its modal) can no longer fire (pipeline.py:141).
