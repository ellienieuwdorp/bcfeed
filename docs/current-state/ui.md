# Current state: UI and visual design

Factual description of the UI as shipped at commit `e363bf4`, based on a full read of `dashboard.css` (1058 lines), `dashboard.html` (306 lines), cross-checks against `dashboard.js` (2113 lines), contrast measurements, and the screenshots in [`screenshots/`](screenshots/). Finding IDs (UI-n, UX-n, JS-n) refer to the verified audit results. This document describes; it does not prescribe.

**Baseline note (re-validated 2026-07-05).** The original audit was written against `598a9dd`; the repo has since fast-forwarded to `e363bf4`, which merged the IMAP-email-provider PR. Two changes matter for this document. First, the **Settings modal was redesigned** — see the new Generation 4 in §1 and the post-merge captures `screenshots/22b-postmerge-settings-panel-{light,dark}.png` and `screenshots/23-postmerge-provider-{gmail,imap}-light.png`. Second, the CSS diff is **purely additive**: the 220 new lines were appended after css:836, so every `css:NN` reference in this document below line 836 remains exact; the new settings styles live at css:841-1058. In `dashboard.html` everything up to line 114 is unchanged (so `html:NN` refs ≤114 still hold), but the settings-modal block was rewritten and its line numbers moved (now html:116-267). Older screenshots (`screenshots/03-settings-light.png`, `screenshots/04-load-creds-modal-light.png`) show the **pre-merge** Settings/Load-Credentials modals and are marked as such where cited.

## 1. The design language, honestly

The intended aesthetic is a dark, mildly neon "mission-control" dashboard: deep slate surfaces (`#0f1116` / `#181b22`), a cyan accent, pill badges, uppercase letterspaced microlabels, a dense 14px data grid with 1.05 line-height, ambient pink/cyan radial glows behind the content (css:33-34), and a universal `translateY(-1px)` hover-lift (css:83, 130, 565). As a dark-mode-only artifact it is reasonably coherent — see `screenshots/10-populated-dark.png` — and every load-bearing contrast pair sampled in dark mode passes AA comfortably (Populate button 8.7:1, log text 6.7:1, error bar 10.8:1).

The language was designed once, on dark, and never finished. It is visibly stratified into **four generations** that coexist on screen — the fourth added by the `e363bf4` Settings redesign, which is the first stratum built substantially the right way:

### Generation 1 — the tokenized base layer

The oldest and most systematic code: the `:root` token block, table, rows, base buttons, filter list, and detail panel. These consistently consume `--surface` / `--border` / `--radius` / `--shadow` and share the hover-lift idiom. This layer *is* the design system, such as it exists.

### Generation 2 — the wireframe-promoted calendar layer

The calendar/date-range sidebar is literal wireframe scaffolding promoted to production (UI-7). The class names say so: `.wireframe-panel` (dashed 1px border, css:261-273) and `.wireframe-body` (diagonal repeating-gradient hatch fill, css:349-361). This layer invents its own conventions on top of half-used tokens:

- its own 3/5/7px spacing rhythm (css:378, 384, 397, 401, 409, 435) against the app's 4/8/12/16 elsewhere
- its own 6px button radius (css:408, 426) against the base 8px/10px
- a second, untokenized blue family (`#64a8ff` / `rgba(100,168,255,…)`) for the most important actions
- the app's only glow rings (static box-shadows, css:528, 553, 559 — no keyframe animations exist anywhere)
- 10-11px type (css:413, 429, 436)

Visible in every sidebar screenshot: `screenshots/02-empty-dashboard-light.png`, `screenshots/10-populated-light.png`, `screenshots/15-label-filters.png`. The dashed idiom also leaks into the expanded row's description box (`.detail-desc`, css:721-733; `screenshots/12-row-expanded-light.png`).

### Generation 3 — the legacy inline-styled modal layer

The secondary modals that the redesign did *not* touch — Credentials Needed and Load Credentials (the `.missing-token-modal` shell, inline-styled headers at html:276, 288 and inline flex footers at html:281, 297) plus the max-results and server-down alerts — remain built almost entirely from inline styles. Their copy was retouched in the merge (see §6) but their construction was not. The max-results and server-down modals still abandon the modal conventions entirely: 12px radius instead of the 10px token, bespoke shadows, 0.75 backdrop instead of 0.45, z-index 9999 instead of 50 (css:585-605, 806-826). At `598a9dd` these surfaces read as "best taste, worst discipline" (UI-10); at `e363bf4` the Settings modal graduated out of this group (below), leaving Gen 3 as the app's calmest-looking but least-disciplined layer.

### Generation 4 — the redesigned Settings panel (`e363bf4`)

The Settings modal was rebuilt in the IMAP-provider merge and is now, by construction, the **most systematic layer in the app** — inverting the old UI-10 finding that the newest surfaces had the best taste and the worst discipline. The redesign introduces a genuine class system that consumes tokens throughout: `.settings-header` (css:851), `.settings-content-scroll` (css:880), `.settings-section` / `.settings-section-title` / `.settings-group` (css:886+), `.provider-panel` (css:964), `.settings-actions`, and the app's **first real form-control styling** — `.form-input`, `.form-select`, `.form-label`, `.help-text` (css:912+). It also adds two reusable button variants, `.button.primary` (`background: var(--accent); color: var(--bg)`, css:1035) and `.button.danger` (css:1044-1052). The panel is a three-section, vertically-scrolling sheet — Appearance / Email Configuration / Data & Storage — with a divider-ruled header and a `max-height:75vh` scroll body (css:880-883; html:116-267). It themes correctly in both modes: the primary action is accent-blue on light and cyan on dark, inputs carry visible tokenized borders, and the destructive Revoke link is a proper outlined-red button — see `screenshots/22b-postmerge-settings-panel-light.png`, `screenshots/22b-postmerge-settings-panel-dark.png`, and the provider variants `screenshots/23-postmerge-provider-gmail-light.png` / `screenshots/23-postmerge-provider-imap-light.png`.

The discipline is not total, and three regressions ride along: (a) the IMAP provider panel's two-column layout is built from raw inline flex (`style="display:flex; gap:24px…"` with nested flex children, html:175-216), so inline-style sprawl did not disappear — it relocated; (b) `.button.danger` and the new focus ring reintroduce untokenized literals — `#ff6b6b` / `rgba(255,107,107,…)` at css:1044-1052 (though this at least reuses the existing show-only-checkbox red rather than inventing the old ad-hoc `#b83a3a`), plus a hardcoded cyan `rgba(82,208,255,0.15)` focus glow at css:940 that does not retheme; (c) the redesign was applied **only** to Settings, so its four sibling modals (Gen 3) and the entire Gen 1/Gen 2 shell around it were left untouched — the divergence between the best and worst surfaces widened rather than closing.

Net: the merge added the strongest evidence yet that the token layer *can* be used properly — the whole Settings redesign is class-based and tokenized — while leaving every other stratum (the wireframe sidebar, the legacy modals, the Populate button that is unreadable in light mode) exactly as the audit found it. The older code defined tokens and mostly used them; the redesigned Settings panel uses them well; the rest of the newer code still bypasses the token layer and styles ad hoc in HTML. The divergence remains architectural (inline styles vs classes), chromatic (untokenized reds and blues), and geometric (new radius/backdrop/z conventions) — now with one exemplary counter-surface proving it was avoidable.

## 2. Design token inventory (summary)

### CSS variables — the only tokenized values

Eleven variables, defined in `:root` (dark = default, css:1-13) and re-declared by `.theme-light` (css:14-25): `--bg`, `--surface`, `--panel`, `--accent` (dark `#52d0ff` cyan / light `#1f7aff` blue), `--text`, `--muted`, `--border`, `--shadow`, `--radius` (10px), `--row-bg`, `--row-unseen-bg`.

**Bug:** `var(--header-bg)` is referenced at css:64 but never defined anywhere — the header background silently computes to transparent and relies only on `backdrop-filter: blur(12px)` (css:65).

### Everything not in a variable

- **Hardcoded accent-cyan copies** of dark `--accent`: `rgba(82,208,255,…)` at css:33, 59, 152, 159, 507-508, 552-553, 566, 581-582, 682, 690-692, and now the redesigned settings-form focus ring at css:940. These never retheme (see §4).
- **A second blue family, never tokenized:** `#64a8ff` / `rgba(100,168,255,…)` on the Populate button (html:52), calendar unseen pills and dots (css:503, 526-528), back-to-top (css:244-245), and every log line (dashboard.js:565, 570). Light mode adds `rgba(64,150,210,…)` (css:558-559) — a fourth blue overall (UI-11).
- **Four unrelated reds, still no danger token:** `#ff5f5f` (row/calendar dots, css:108, 534), `#ff6b6b` (show-only checkbox accent, css:223 — the `e363bf4` redesign now also routes the Revoke button through this literal via `.button.danger`, css:1044-1052), `#b83a3a` (error border, now only in the status error bar, html:85; the old inline `#b83a3a` Revoke link is gone), `#ffc5c5` (error text, html:85). The redesign consolidated the danger red slightly (reusing `#ff6b6b` instead of inventing a fifth) but still tokenized none of them.
- **Gold star family:** `#f2d45c` + tints (css:135-138, 679).
- **Decorative gradient tints:** hot pink `rgba(255,105,180,0.08)` in the dark body background (css:34), orange `rgba(255,171,64,0.1)` in light (css:43).
- **White-alpha overlays everywhere** (`rgba(255,255,255,0.02…0.36)`) as control fills, hatches, and inset highlights (css:74, 124, 282-288, 355-359, 406, 424, 477, 492, 540-542) — all dark-tuned; they vanish on white (see §4).

### Typography

- One font stack, `"Inter", "Helvetica Neue", Arial, sans-serif` (css:37) — Inter is never loaded (no `@font-face`/`<link>`), so machines without it silently fall back. No monospace stack anywhere, including the status log.
- **11 font sizes with no scale** (22/20/18/16/15/14/13/12/11/10px), 10px minimum on the CACHED badge, Today button, and sort indicator (css:154, 429, 669).
- Five micro letter-spacing values (0.2-0.6px), no system.
- `line-height: 1.05` on table cells and filter items (css:211, 651).
- Uppercase implemented two ways: CSS `text-transform` (css:156, 189, 347, 420, 656) *and* literally capitalized HTML text ("FILTER BY DATE" html:15, "SHIFT-CLICK TO SELECT RANGE" html:39, "SELECTED DATE RANGE:" html:51, "SHOW ONLY:" html:76).

### Spacing, radii, shadows, motion, z-index

- **Spacing:** 18+ distinct px values, untokenized; calendar cluster uses 3/5/7px while everything else uses 4/8/12/16; four-plus different modal paddings. The old literal spacer divs in the Settings modal are gone (replaced by `.settings-section`/`.settings-group` gaps in the redesign), but the redesign added its own untokenized spacing rhythm (20/24/28px section padding, 15/24px inline IMAP-column gaps, css:851-1058; html:175-216).
- **Radii:** six values — 6, 8, `calc(10px - 2px)`, 10 (token), 12, 999px/50%. Buttons (8px) never match panels (10px) or the newest modals (12px) (§1.5 of the CSS map).
- **Shadows:** a `--shadow` token exists and is used 5 times; 15+ hardcoded one-off shadows exist anyway (css:84, 132, 248, 272, 553, 559, 567, 600, 821, …).
- **Motion:** no `@keyframes` at all. Four near-identical hover durations (0.1/0.12/0.15/0.2s), `transition: all` on `.button` and `.star-btn` (css:78, 127), hover-lift as the universal cue.
- **Z-index:** 2 / 5 / 6 / 20 / 50 / 9999, unscaled; the 50-vs-9999 split is why server-down always beats settings (css:592, 751, 813).

### Dead CSS

`.pill` (css:687-702), `.inline-link` (css:52-56), `.calendar-row` (css:367-373) are unreferenced in HTML and JS (grep-verified). `.calendar-day.selected` duplicates `.calendar-day.in-range` verbatim (css:580-584 vs 506-509). Notably, the entire `.calendar-day.scraped` family — including its glow-ring rules (css:539-561) — is dead: dashboard.js:1260 applies the class `unseen-day`, not `scraped`, so the only live "populated" treatment is the blue pill from `.unseen-day .date-label` (UI-5 correction).

## 4. Theming state: light mode is ~60% broken

Mechanism: JS toggles `.theme-light` on `<body>` (dashboard.js:279) from the settings checkbox; `.theme-light` re-declares the 11 variables. Only three light-specific rule overrides exist beyond the variables (body gradient plus two calendar rules that target the dead `.scraped` class). Everything else "themes" only if it happens to consume a variable — and much of it does not. Dark is the only finished theme (UI-4).

Concrete breakages, with measured WCAG ratios:

1. **The primary Populate button is unreadable: 1.34:1, ~1.06:1 disabled** (UI-1, high). Inline white text on `rgba(100,168,255,0.35)` (html:52) composites to white-on-pale-blue; with `.button:disabled` opacity 0.45 (css:86-92) the label is effectively invisible. See `screenshots/01-first-run-light.png`, `screenshots/06-populate-error-light.png`, `screenshots/10-populated-light.png` — the same button is 8.70:1 in `screenshots/10-populated-dark.png`.
2. **Populated calendar-day numbers are illegible: 1.26:1** (UI-2, high). `.unseen-day .date-label` forces `#fff` on `rgba(100,168,255,0.28)` over a white card (css:502-505). In `screenshots/10-populated-light.png` nearly every June day number is a ghost digit while the few unpopulated days (10, 11) are crisp black.
3. **Error feedback is unreadable: 1.29:1** (UI-3, high). Inline `#ffc5c5` on `rgba(184,58,58,0.1)` (html:85) is tuned for dark (10.78:1 there). Compounding: the captured error state (`screenshots/06-populate-error-light.png`) shows an empty Status box and no error text anywhere — the failure produced zero visible feedback (UX-3).
4. **Status log text: 2.45:1** at 12px (fails AA; dark is 6.70:1) — hardcoded `#64a8ff` (dashboard.js:565, 570).
5. **CACHED badge: 3.65:1** at 10px bold (fails AA; dark is 7.23:1) — hardcoded cyan tints under light-blue accent text (css:146-161; UI-13).
6. **Control fills vanish.** Every button/nav/scrollbox fill is a `rgba(255,255,255,0.02-0.06)` overlay (css:74, 124, 406, 424, 477, 492) — white on white in light mode, so "Mark as seen", calendar nav, and Today reduce to hairline outlines (`screenshots/02-empty-dashboard-light.png`).
7. **Accent tints don't retheme.** Every cyan tint is hardcoded to dark's `#52d0ff` (css:59, 152, 159, 507-508, 566, 581-582, 690-692), so light mode mixes its `#1f7aff` accent with leftover cyan chrome — up to four blues visible simultaneously in `screenshots/10-populated-light.png` (UI-11).

Root causes are exactly two: white-alpha fills that assume a dark backdrop, and hardcoded accent/blue literals that bypass `--accent`. The controls that theme correctly by construction are `.toggle-button.toggle-active` (`background: var(--accent); color: var(--bg)`, css:93-97) and — new at `e363bf4` — the **entire redesigned Settings modal**, which consumes `--bg` / `--border` / `--accent` / `--muted` throughout and therefore renders correctly in both light and dark (compare `screenshots/22b-postmerge-settings-panel-light.png` and `-dark.png`). It is the clearest proof that the light-mode breakages above are the result of bypassing the tokens, not of the token system being incapable. The one retheme gap the redesign introduces is minor: the form focus ring is a hardcoded cyan `rgba(82,208,255,0.15)` (css:940) that stays cyan under light's `#1f7aff` accent — visually slight, unlike the §4 failures above.

## 5. Accessibility state

- **Only one designed focus state exists, and it is scoped to the new settings form.** At `598a9dd` there were zero `:focus` rules. `e363bf4` adds exactly one: `.form-input:focus, .form-select:focus` (css:937-941), which does `outline: none` and substitutes an accent border plus a hardcoded cyan `box-shadow` ring. This is a real designed focus cue — but it covers *only* the redesigned settings/IMAP form controls, it removes the native outline it replaces (so if the ring ever fails to render there is no fallback), and its ring color does not retheme (§4). Every other keyboard-focusable element (data rows with `tabIndex=0`, star buttons, links, calendar controls, all other buttons) still has no designed focus state and shows browser-default rings by inherited luck, not design (UI-12).
- **Core controls are unreachable by keyboard, not just unstyled:** calendar day cells are JS-built `<div>`s with click listeners only — no tabindex, role, or key handling, and the shift-click range gesture has no keyboard equivalent (dashboard.js:1235-1322); sortable headers are plain `<th>`s with click handlers, no `aria-sort` (dashboard.js:950-963) (JS-7, UI-12).
- **Modals still have no dialog semantics** — including the redesigned Settings panel: no `role="dialog"`, no `aria-modal`, no focus trap, no Escape handling on any modal (html:116-301); the newly-added IMAP form (host/user/pass/port/folder inputs, html:170-248) is reachable but sits in an untrapped, unlabeled dialog, and the server-down modal has no dismissal at all (JS-7, UX-15). The redesign improved the settings *styling* but added no dialog a11y.
- **The status log — the app's sole feedback channel — has no `aria-live`,** so the longest-running operation is silent to assistive tech (html:102-110).
- **Invisible-but-interactive target:** `.row-dot.read { opacity:0 }` keeps `cursor:pointer` and its click handler on an invisible 10px control (css:113-115; dashboard.js:900-911).
- **Contrast failures** in light mode as itemized in §4 (five failing pairs on primary surfaces); in dark mode, sampled pairs pass.
- **Sub-legible type:** 10px text on the CACHED badge, Today button, and sort indicators (css:154, 429, 669); `line-height:1.05` on data cells risks clipped descenders (css:651).
- Counterpoint worth preserving: the row-level keyboard loop (arrows, Enter/Space, `s`, `u`, Escape — dashboard.js:852-898) is complete and shows the intent existed. It is documented nowhere in UI or docs (UX-14).

## 7. What holds up

For balance, the parts of the current UI that are genuinely working and are explicitly to be preserved: the dense sortable table (the strongest surface in the app), the calendar-as-coverage-map concept (UX-13 calls it the app's best IA idea, even though its current encodings collapse), star-triggers-preload, the complete row-level keyboard loop, the served docs pages (`screenshots/05-docs-readme.png` — arguably the most polished surfaces in the product), and the settings-modal generation's calm, flat visual direction — which at `598a9dd` was the right target language built the wrong way (inline styles; `screenshots/03-settings-light.png`, **pre-merge**), and which the `e363bf4` redesign has now largely realized the right way: a class-based, token-consuming, correctly-theming Settings panel (`screenshots/22b-postmerge-settings-panel-light.png` / `-dark.png`). That redesign is itself now something to preserve and extend — it is the working proof-of-concept for the normalized token/component system the rest of the app still needs, and the first place the "right direction" was also the right construction.
